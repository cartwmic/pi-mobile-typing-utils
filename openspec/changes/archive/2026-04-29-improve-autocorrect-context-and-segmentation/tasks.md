## 3. Trigram side-table (data + module + lazy attach)

- [x] 3.1 Create the build script `scripts/build-trigrams.ts`. It MUST produce an **exactly correct** top-500k trigram list (not an approximation). A naive bounded-heap approach is mathematically wrong because evicted triples may re-occur later in the stream and accumulate counts that would have qualified them for the top-K. The script MUST instead use a **two-pass shard+merge** approach:
  - **Pass 1 (sharding):** stream each source file (decompressing on the fly via `node:zlib.createGunzip()`), filter to `year >= 1990`, lowercase-ASCII-only, and present in either the symspell-ts unigram dictionary OR the shipped tech-dictionary (`data/tech-dictionary.txt`). For each retained `(w1, w2, w3, year_count)`, hash the triple and append the line to one of N shard files (e.g., 64 shards) selected by `hash % N`. This guarantees identical triples land in the same shard.
  - **Pass 2 (merge):** for each shard file, sort by triple and aggregate counts (each triple now appears as a contiguous run within its shard). After aggregation, emit the shard's `(triple, total_count)` pairs into a global candidate pool by maintaining a streaming top-500k min-heap that consumes shards in any order. Because aggregation is exact within a shard and triples are partitioned by hash, the global aggregation is exact.
  - After both passes, emit the top 500,000 in count-descending order to `data/trigram-top500k.tsv` in the format `w1<TAB>w2<TAB>w3<TAB>count<NEWLINE>`.
  - Print summary statistics (total source rows scanned, retained rows, shard sizes, top 10 trigrams) to stderr.
  - Be runnable manually with documented prerequisites in `scripts/README.md`; runtime expectations: ~60–120 minutes wall time, ~2–4 GB peak shard-disk usage, ~500 MB–1 GB peak resident memory (one shard's hash map at a time).
  - Source URL/snapshot is a hardcoded constant at the top of the script with a comment naming the snapshot date.
